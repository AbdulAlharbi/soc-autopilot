SOC Autopilot.

An autonomous multi-agent system that owns the SOC alert triage and incident response workflow end to end — alert in; triaged, investigated, contained, verified, reported and closed out — and where the boundary between acting alone and asking a named human is a YAML policy every action must pass through, not a line in a prompt.

Incident Commander + 5 specialist agents 4 end-to-end scenarios 26 tests passing 4 risk tiers (0–3) runs offline · Claude optional
The problem

Not “can the agent act?” — “does it know when to stop and ask?”

Alert triage is the highest-volume, most repetitive job in a security team, and every response action has a blast radius. Isolating a laptop is an inconvenience; isolating the production ERP server during month-end close is an outage. That combination makes it a real test of agentic automation: the hard part is not capability, it is knowing the limits of your own authority — structurally, not as a suggestion in a system prompt.

Components

One orchestrator, five specialists — one of them able to change the world

BaseAgent.can_write defaults to False and is passed to the tool registry on every call. Only the Responder sets it True. Triage, Investigator, Communicator and Reporter can reach queries and notifications; the containment operations are out of their reach by construction.

Orchestrator

Incident Commander no tool calls

Owns the incident state machine and sequences the specialists. It never calls a tool itself. After every transition it checkpoints both the incident and the whole simulated world, so a crash — or an approval that arrives hours later — resumes rather than restarts.

Shared machinery

Three pieces every agent leans on

The Brain

Agents never talk to a model directly. They hand a task name, a context dict and a pydantic schema to a Brain and get a validated object back — so model output is a proposal that gets checked, never a side effect.

Claude
Messages API, schema embedded in the prompt, JSON unwrapped from prose or fences, one repair round, then it falls through to the rule brain and tags the rationale so the fallback is visible
Heuristic
Explicit rules over the same signals — an additive evidence score with a hard short-circuit for an allowlisted scanner inside its change window. The floor the model must beat, the CI back-end, and the production fallback
src/socpilot/llm/ — base · claude · heuristic

Tool Registry

One choke point between any agent and any system. It validates the operation exists, enforces write authority from the caller's flag, executes, and records the call, parameters and truncated result — failures included, as a distinct tool_error event.

24 ops
12 callable without write authority (7 queries + 5 notification/tracking calls, all tier 0) and 12 containment operations
Catalogue
what the model is shown, so it can only propose operations that actually exist
src/socpilot/tools/registry.py

Hash-chained audit log

Every tool call, decision, approval and state transition is one JSON line whose SHA-256 covers the previous line's hash. socpilot audit walks and verifies the chain, so a rewritten or deleted entry does not go unnoticed.

Tested
a test rewrites a payload field to make a tool call look like its opposite and asserts verification flips to false
Gap
a refused write raises before the audit call, so the refusal itself leaves no entry

The centerpiece

The autonomy policy

140 lines of policy.py with no LLM anywhere in it, driven by config/policy.yaml. Every action carries a base risk tier; the tier is bumped for critical or production assets and for privileged, service or VIP identities; and the action runs autonomously only if the final tier sits at or below the ceiling, triage confidence clears the bar, and the per-incident budget has not run out.

0
Read-only / notify
Queries and the calls that talk to people. Never gated, so the system can always reach a human mid-approval.
  • siem.search
  • threat_intel.lookup
  • chat.post · mail.send
  • ticketing.*
1
Narrow & reversible
One process, one IP, one message. Small blast radius.
  • firewall.block_ip
  • edr.kill_process
  • edr.collect_forensics
  • email_gateway.quarantine_message
2
Disrupts one user/host
The autonomy ceiling by default: the agents may go this far alone.
  • edr.isolate_host
  • iam.revoke_sessions_and_reset_password
  • iam.enforce_mfa_reregistration
3
Disrupts the business
Always a human. Reached directly, or by a bump from tier 2.
  • iam.disable_user
  • firewall.block_subnet
  • edr.wipe_host *
  • iam.delete_user *

* edr.wipe_host and iam.delete_user are on the never-automate list but are deliberately not implemented in the registry — the guard exists before the capability does. Tier colours match the CLI's own output.

Asset bump. If the action names a host, the inventory is consulted: +1 if criticality is critical, +1 if the environment is production. SRV-ERP-01 is both, so isolating it goes 2 → 3.
Identity bump. If the action names a user, the directory is consulted: +1 privileged, +1 service account, +1 VIP. A password reset is tier 2 for an analyst and tier 3 for a sysadmin.
bump_min_base_tier: 2 — the rule that makes it usable. Bumps only escalate actions that are already disruptive. Killing one process or collecting forensics on the critical ERP server stays tier 1 and runs autonomously; isolating that same server stops for a human. Without it, everything touching production would need approval — approval fatigue, and the pattern that gets automation switched off.
Fail closed. An operation with no entry in base_tiers and no tool.* wildcard defaults to tier 3. Adding a tool without adding a tier makes it human-gated, never silently automatic.

always ask a named human, whatever the tier

  • iam.disable_user disabling any account is a business decision
  • firewall.block_subnet estate-wide blast radius

never automate — checked first, absolute

  • edr.wipe_host not runnable even with chat approval
  • iam.delete_user not runnable even with chat approval

The verdict is not just a boolean — the reason string travels with the action into the CLI table, the approval request the human reads, and the report.

The data

A small, coherent enterprise to act on

Ten simulated systems back the tool registry — seven of them loaded from the JSON files in data/fixtures/ — and they are stateful on purpose: isolating a host changes what the EDR returns afterwards, and removing a mailbox rule really deletes it — which is what lets the Responder verify its own containment by reading the system back. The same users, hosts and indicators recur across SIEM, EDR and threat intel, so an investigation has something real to pivot through.

Verified & not verified

What is proven, and what is only implemented

Exercised offline, every run

26 tests — 8 policy, 5 templating, 9 end-to-end workflow, 4 Claude-contract — plus run-all, both on Python 3.11 and 3.12 in CI. No test makes a network call.

  • The autonomy boundary, pinned operation by operation: workstation isolation runs alone, the identical operation on a critical production server is tier 3 and gated, and a tier-1 action on that same server is not bumped.
  • Containment reaches the systems — tests assert the state of the world (user in the reset set, IP in the block list, messages quarantined, mailbox rule gone), not the agents' account of it.
  • Deferred approval survives a process boundary — the incident is reloaded in a brand-new commander and resumed to resolved.
  • The audit chain detects tampering — a rewritten payload flips verification to false.

Implemented, not proven known gaps

Taken from the repository's own Known gaps section — stated here at the same confidence.

  • Write-authority refusals are not audited. The registry raises before the audit call, so a refused write leaves no log entry. The refusal works but has no dedicated test.
  • Escalation on unverifiable containment is untested. The commander escalates when an executed action reports verified is False, but no test forces that state; the tested escalation path is human denial.
  • The Claude path is contract-tested, not live-tested. A stubbed client covers JSON extraction, the single repair round and the heuristic fallback; a live run needs an API key and is not exercised in CI.
  • Single-process assumption. The world snapshot has no locking, so two concurrent incidents in separate processes would clobber each other.
  • The enterprise systems are simulated. Nothing here talks to a real SIEM, EDR or identity provider.
Run it

Clone, install, watch it work

Python 3.11+ with pydantic, typer, rich and pyyaml. The anthropic SDK is an optional extra — without an API key the deterministic rule brain runs the entire workflow, which is what lets CI and the demo work with no network. 

# install
$ git clone https://github.com/AbdulAlharbi/soc-autopilot && cd soc-autopilot
$ python -m venv .venv && source .venv/bin/activate
$ pip install -e ".[dev]"

# see what is bundled, then run everything
$ socpilot scenarios
$ socpilot run-all --brain heuristic

# be the human in the loop on the ransomware case
$ socpilot run ransomware-precursor-server

# or defer the decisions and pick them up from another shell,
# the way a Slack approval would work in production
$ socpilot run ransomware-precursor-server --approvals defer
$ socpilot show INC-XXXXXXXX
$ socpilot decide INC-XXXXXXXX ACT-YYYYYYYY --approve --as f.zahrani -c "maintenance window open"

# the trail, and whether anyone edited it
$ socpilot audit

# 26 tests, no network, under a second
$ pytest -q

With ANTHROPIC_API_KEY set, the default SOCPILOT_BRAIN=auto selects Claude; without it, the heuristic brain. config/policy.yaml is the whole autonomy contract — drop auto_execute_max_tier to 1 and the agents ask before resetting anyone's password.
